OmniEvolve Phase 1: LJ924 and Occam’s Circuit

https://github.com/QuantumBFS/quantum.harness/pull/181

The pipeline worked, but Phase 1 did not produce a competitive breakthrough: Occam reached a 399-gate exact solution, while LJ924 never beat its incumbent.

Challenge

What was attempted and what counts as success.

Phase 1 tested whether LLM-guided program evolution could solve two very different optimization challenges in one reusable framework. LJ924 asks for a lower-energy 924-atom Lennard–Jones cluster with strict force convergence. Occam’s Circuit asks for exact hidden Boolean functions using as few gates as possible.

Significance

Both tasks have hard, independent verification and an unambiguous ordering of valid solutions. A successful campaign would therefore demonstrate genuine algorithm discovery rather than subjective LLM code quality.

Why the two searches stalled
  • Occam has an exactness cliff: global natural-language rewrites often save gates by breaking a rare truth-table case. The missing primitive is formal local synthesis or equivalence-preserving peephole search.
  • LJ starts from an exceptionally well-relaxed incumbent. Single-core local perturbations usually return to the same basin or retain excessive force, while meaningful basin crossing needs a different search algorithm and much more parallel compute.
  • Failure memory and dense feedback improved diagnosis, but feedback cannot compensate for a candidate representation that does not expose safe, composable improvements.

Highlight and Next Phase

What is retained, what is archived, and why #229 is next.

What is genuinely reusable

Phase 1 produced an auditable evolution stack: behavioral counterexamples, proposal-versus-incumbent separation, durable failure memory, cross-provider fallback and content-addressed candidate history. These are infrastructure results, not substitutes for a winning solution.

Phase 1 decision

Archive both brute-force campaigns. Preserve the Occam generation-15 397-gate candidate as a one-counterexample repair lead, but do not spend additional LLM generations on either task without changing the search representation.

Recommended Phase 2: issue #229

Automated symmetry reduction for noncommutative moment hierarchies is a better OmniEvolve target because each mutation can be checked for exact or solver-tolerance equivalence, while block-size reduction and runtime provide continuous progress.

Bottom line The day was not a competitive success. Its useful conclusion is narrower and actionable: OmniEvolve needs verifier-bounded, composable candidate transformations. Issue #229 naturally supplies that structure; LJ924 does not, and Occam requires a formal synthesis backend before more evolution is justified.
