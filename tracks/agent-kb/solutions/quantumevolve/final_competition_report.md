## A. 总体概述

### A.1 比赛目标

本次比赛的核心目的不是在某个物理赛道上打败已知最优解，也不是成功复现某个特定论文的结果。**核心目标是验证一个科学命题：LLM 驱动的进化代码优化能否在科研问题上实现突破？**

具体而言，我们试图回答以下问题：
- LLM 进化在什么场景下有效？什么场景下无效？
- 进化产生的"改进"是真创新还是表面调参？
- LLM 会如何尝试作弊？如何防御？
- 从零专业知识出发，evolve 能否替代领域专家？
- 框架需要怎样改进才能更有效？

### A.2 方法论

我们采用 OmniEvolve 框架——一个自主开发的受控元进化框架（Controlled Meta-Evolution Framework）。OmniEvolve 是在比赛期间独立设计和实现的，吸收了 AlphaEvolve、ShinkaEvolve、MLEvolve 等系统的设计理念（如 SEARCH/REPLACE diff、多级新颖性门、渐进式探索调度），但并非任何已有框架的复现或移植。其独有特性包括：

- **双循环架构**：Fast Loop（单代候选进化 11 步）+ Slow Loop（策略窗口评估与受控元进化）
- **渐进式 MCGS 搜索**：MCTS 引导的父代选择，支持多父代交叉融合、岛屿模型与停滞检测
- **受控元进化**：L0/L1/L2 风险分级，Champion-Challenger 模式，评估语义永久不可变
- **多级新颖性门**：Embedding → AST → 行为签名 → 可选 LLM 裁判，防止重复探索
- **分层记忆 L0-L4**：分支级 → 实验级 → 任务族 → 领域 → 全局，混合 FTS5 + 向量检索

其核心进化循环为：

1. **种子代码**（initial_code.py）：人工编写一个正确但弱的基线实现
2. **LLM 生成**：LLM（qwen3.8-max-preview）在种子基础上提出变异策略
3. **沙箱评估**（evaluator.py + verify_*.py）：在隔离沙箱中运行候选代码并打分
4. **选择与变异**：基于 score 的 MCTS + 进化策略选择父代，进入下一代

每个赛题的框架由三件套构成：
- **initial_code.py**：种子候选（故意弱，留出进化空间）
- **evaluator.py**：评估器（定义 score 函数 + 沙箱执行计划）
- **config.toml**：进化参数（LLM 模型、种群大小、代数、沙箱限制）
- **verify_*.py**（部分赛题）：独立验证器（反作弊 + 数学验证）

## B. 逐题详细分析

### B.1 #71 Occam's Circuit（布尔函数最小电路恢复）

#### 问题描述与官方要求

#71 是一道带 `accepted` 标签的官方赛题。任务是从多项式级的输入-输出训练样本中恢复一个隐藏的布尔函数，并给出**最小且能泛化**的电路实现。官方最终交付包括 4 个 mystery 电路的恢复结果、测试输出预测、搜索脚本和方法说明。

该问题的数学本质是 NP 困难的电路最小化问题（circuit minimization），在经典 EDA 领域也没有通用的高效算法。OmniEvolve 的任务不是替代 SAT 求解器，而是让 LLM 在给定种子代码的基础上，探索更优的电路结构或搜索策略。

#### 种子代码策略与初始状态

种子代码实现了一个基于真值表匹配的贪心搜索：对每个 mystery 实例，先用穷举枚举所有可能的门组合，找到第一个能匹配全部训练样本的最小电路。对 practice-add-n4 实例（6-bit 加法），种子已达到 100% accuracy、17 gates、score=0.9958。

种子故意使用了朴素的深度优先枚举策略——没有利用布尔代数化简（Quine-McCluskey）、没有利用对称性、没有利用 BDD（Binary Decision Diagram）。这些是 LLM 可以探索的改进方向。

#### Evaluator / Verify 架构设计

评估器采用两步验证架构：
1. main.py 候选代码运行在沙箱中，对 4 个 mystery 实例逐一尝试恢复电路
2. evaluator 检查：(a) 训练集 accuracy 是否 100%；(b) 门数是否小于等于当前最佳；(c) 测试集 prediction 是否自洽

score = 0.5 * accuracy_component + 0.3 * gate_count_component + 0.2 * generalization_component。这个设计的关键在于 gate_count_component 是连续的——门数越少分越高——给了 LLM 明确的优化方向。

#### 进化迭代轨迹

Occam 是投入最大的赛题（31 DBs, 4.28M tokens），其迭代轨迹呈现出一个反复出现的模式：

**最佳 run（v15, 22 evals）的逐代 score 变化：**
```
gen= 0  score=0.9958  ← 种子基线
ngen= 1  score=0.9959  ← 微提升（可能微调了搜索顺序）
gen= 2  score=0.0059  ← 悬崖式回退（accuracy 丢失）
gen= 3  score=0.9960  ← 达到最高分
ngen= 4  score=0.9960  ← 持平
gen= 5-7  score≈0.006  ← 再次悬崖式回退
gen= 8  score=0.9958  ← 恢复
gen= 9-10 score≈0.006  ← 回退
gen=11-18 score≈0.996  ← 在峰值附近震荡
gen=19-21 score≈0.006  ← 最终回退，未恢复
```

这个轨迹揭示了一个核心问题：**score 悬崖效应**。当 LLM 尝试减少门数时，稍有差池就导致 accuracy 从 100% 跌到 0%，score 从 0.996 直接跌到 0.006——没有中间状态。

在全部 31 个 DB 的 208 次评估中，最高分始终停在 0.9960，从未达到 1.0。

#### 成功分析

1. **种子代码质量高**：种子已经达到 score=0.9958（100% accuracy, 17 gates），进化只需微调
2. **评估器设计合理**：同时考核训练集 accuracy 和门数紧度，给了 LLM 明确的优化方向
3. **多实例 suite 评估**：v12+ 切换到 4 个 mystery 联合评估，比单实例更鲁棒
4. **LLM 确实在尝试不同的搜索策略**：从日志中可以看到 LLM 提出了 BDD、Karnaugh map、符号化简等方向——虽然大部分没有成功实现

#### 失败分析

1. **0.996→1.0 的 gap 无法跨越**：最后 0.4% 需要将门数从 17 减到更少。对于 6-bit 加法器的 mystery，最小电路可能就是 17 门——如果答案已经是 17 门，则 score=1.0 需要在其他实例上取得更好成绩
2. **score 悬崖效应导致学习困难**：accuracy 从 100% 到 0% 是离散跳变，LLM 无法从 score=0.006 的失败候选中提取有用信息——它只知道"这个改动破坏了正确性"，但不知道如何修正
3. **震荡而非收敛**：gen 5-7、9-10、19-21 的反复回退说明 MCTS 探索在已知不好的区域浪费了大量 budget。如果配置 max_stagnation_gens=6，本应在 gen=9 就停止
4. **LLM 对布尔代数化简的实现能力有限**：虽然 LLM 知道 Quine-McCluskey 和 BDD 的概念，但在代码层面正确实现这些算法并集成到搜索流程中，超出了其能力范围

#### 作弊分析

Occam 赛题没有发现明确的作弊行为。这是因为评估器的设计天然防止了硬编码作弊——候选代码必须对 4 个 mystery 实例给出正确输出，而 mystery 的测试集是隐藏的。LLM 无法预知测试集，因此无法硬编码答案。

不过，一个潜在漏洞是：如果候选代码对训练集做了过拟合（memorize 训练样本而非学习通用函数），score 可能虚高。评估器的 generalization_component 部分缓解了这个问题，但不够严格。

#### 反思与改进方向

- **score 设计应该平滑**：如果 evaluator 对"门数减少但 accuracy 不完美"给出部分分数（例如 0.8*accuracy + 0.2*(1-gate_ratio)），而非在 accuracy<100% 时直接归零，进化会有更好的梯度信号
- **early stopping 有价值**：v15 在 gen=3 就达到峰值，后面 18 代全是在峰值附近震荡——浪费了约 80% 的计算预算
- **需要更多 mystery 实例的多样性**：4 个实例中如果某些已经达到了最小门数，进化应该聚焦在还没满分的实例上

### B.2 #117 Lennard-Jones 团簇全局优化

#### 问题描述与官方要求

#117 要求打破单组分 Lennard-Jones（LJ）团簇的能量记录。LJ 势是一种经典的原子间相互作用模型，全局最小化 LJ 团簇能量是计算化学和材料科学中的经典 NP 困难问题。

官方明确指出：LJ38（E_GM = −173.928427）是已知困难基准，只用于训练与效率比较。**复现已知 E_GM 不算最终成果**——必须打破记录。

该问题没有 `accepted` 标签，是开放 challenge。

#### 种子代码策略与初始状态

种子代码实现了一个基于 L-BFGS 梯度下降的局部优化器，从随机初始构型出发优化原子位置。种子在 LJ38 上达到 E = −173.134317，力范数 5.2×10⁻⁴，score = 0.983407。

关键缺陷：种子只做单点局部优化，没有全局搜索策略（如 basin hopping、遗传算法、模拟退火）。这意味着它必然陷入离起点最近的局部最优。

#### Evaluator / Verify 架构设计

评估器采用两步验证：
1. main.py 候选代码运行 LJ 优化，输出最终构型和能量
2. verify_lj.py 独立验证：(a) 重新计算能量确保一致；(b) 检查力范数是否收敛；(c) 与已知 E_GM 比较给出 gap

score = (S_known − E_candidate) / (S_known − S_seed)，其中 S_known 是已知最优能量。这个归一化设计有一个致命问题：当候选能量接近种子时 score 接近 0，接近已知最优时 score 接近 1.0——但 score=1.0 只代表复现了已知最优，不代表打破了记录。

后续的 frontier evaluator 对 LJ924 等大体系使用了不同的归一化，使得种子在大体系上已经 score=1.0。

#### 进化迭代轨迹

**初始 GLM run（lj_glm52_parent_smoke3.db, 4 evals）：**
```
gen=0  score=0.9834  E=−173.1343  force=5.2×10⁻⁴  fevals=218,233  ← 种子
ngen=1a score=0.9834  E=−173.1343  force=5.2×10⁻⁴  fevals=187,063  ← 效率↑14%
gen=1b score=0.9834  E=−173.1343  force=5.2×10⁻⁴  fevals=185,721  ← 效率↑15%
gen=1c score=0.9834  E=−173.1343  force=3.0×10⁻⁴  fevals=229,781  ← 局部更好但未跨漏斗
```

**所有候选能量完全一致（−173.1343），进化陷入同一能量盆地。**

后续 20+ DB 的 frontier run 在 LJ924 等大体系上 score=1.0，但这只是 evaluator 归一化的假象——种子本身就是一个成熟的 LJ 优化器，在大体系上已经足够好。

#### 成功分析（框架层面）

1. **框架链路完整打通**：从种子代码到沙箱评估到分数反馈，端到端跑通
2. **两步验证架构有效**：verify_lj.py 独立重算能量和力范数，防止了坐标注入作弊
3. **力范数评估比纯能量更严格**：同时考核能量和受力收敛，排除了"能量低但构型不稳定"的假阳性
4. **效率优化确实有效**：gen=1a/1b 将力评估次数降低了 14-15%，说明 LLM 找到了减少不必要梯度计算的策略

#### 失败分析

1. **LJ38 双漏斗地形**：E = −173.13 对应 FCC-like 局部最优，跨越到 E = −173.93 的 icosa 全局最优需要大规模结构重排——这种重排不是调参能实现的，需要完全不同的搜索策略。LJ38 的双漏斗（FCC/ico）是文献中 30 年的经典挑战，Basin hopping、遗传算法、thermal cycling 等全局优化技术都是为此设计的。但种子代码只用了 L-BFGS 单点优化，从根本上缺乏跨漏斗能力
2. **进化优化的是优化器参数而非搜索策略**：LLM 的变异都集中在调整 L-BFGS 的步长、容差、最大迭代次数——没有发明新的全局搜索机制。从 Director LLM 的日志可以看到它确实提出了 FCC/icosa 模板、双尺度扰动和 adaptive reheating 等概念，但这些概念在 Coder LLM 的代码层面未能正确实现
3. **所有候选困在同一盆地**：4 个候选的能量完全一致到小数点后 4 位，说明起点和搜索路径都收敛到同一局部最优——缺乏多样性。根源是种子从单一随机种子出发优化
4. **score=1.0 的误导**：LJ924 frontier 的 score=1.0 让人误以为任务完成，实际上只是种子在大体系上已经接近已知最优——进化并未实质改进算法
5. **框架层面的问题**：任务被错误命名为 `initial_code`（F-01）导致 LLM 不知道自己在优化 LJ；父代选择 bug（F-02）导致高分候选无法被选为 parent；评估反馈过慢（F-06）使得每代需 7 分钟。这些框架 bug 消耗了大量调试时间

#### 作弊分析

LJ 赛题没有发现作弊行为。verify_lj.py 通过独立重算能量有效防止了坐标注入。不过理论上 LLM 可以通过在代码中硬编码已知最优构型来作弊——verify_lj.py 的力范数检查可以部分检测这种行为（硬编码构型的力范数应该很小，但如果 LLM 硬编码了一个不精确的构型，力范数会暴露差异）。

#### 反思与改进方向

- **全局优化问题的进化需要搜索策略层面的变异**：不是调参，而是让 LLM 发明全新的搜索范式（如"从多个随机起点做局部优化然后取最优"、"在局部最优附近做随机扰动后重新优化"）。这需要种子代码的结构有足够的变异空间——当前种子是一个单点 L-BFGS，LLM 很难在不重写整个代码的情况下添加全局搜索
- **score=1.0 ≠ 任务完成**：evaluator 的归一化分数容易被误读。应该额外输出绝对能量值和与记录的 gap
- **双漏斗问题是经典困难**：LJ38 的 FCC/ico 双漏斗是文献中 30 年的经典挑战。期望 LLM 在几代进化中解决是不现实的——但进化应该至少探索不同的搜索范式

### B.3 #232 非对易多项式优化（量子图参数 β(G) 的严格证书）

#### 问题描述与官方要求

#232 要求利用 moment-SOS / SOHS（Sums of Hermitian Squares）层级，对量子图参数 β(G)——Lovász ψ 函数的非对易推广——给出严格的上界证书。目标图来自 arXiv:2310.00612 Table 4。

β(G) 是一个非对易多项式优化问题：给定图 G，定义投影矩阵 A_i 满足 A_i² = A_i 且 A_i A_j = 0 对非相邻顶点，求 max Σ Tr(A_i) / Tr(I)。这与量子信息中的 Lovász 数有关，但允许非对易变量。

"精确闭合"意味着证明 upper = lower = α(G)（独立数），即 β(G) = α(G)。

#### 种子代码策略与初始状态

种子代码实现了一个 level-1 SOHS 松弛：构造 degree-2 的 Hermitian 基词，在 cvxpy 中建立 SDP，求解 β(G) 的上界。对 graph33（5 顶点图），种子给出 upper = 2.00249，score = 0.500。

种子的弱点是基词太少（只有 degree-2），且没有利用图的对称性。进化目标是增加更高次基词来收紧上界。

#### Evaluator / Verify 架构设计

这是所有赛题中验证架构最严格的：
1. main.py 候选代码运行 SDP，输出数值上界
2. verify_dual_certificate.py 独立验证器：
   - 用纯 Python Fraction（精确有理算术）重建代数
   - 验证 225 条仿射系数恒等式
   - 对 45×45 有理 Gram 矩阵执行无主元 LDL 分解
   - 45 个主元全部严格为正 → 证书有效

这个验证器**完全不信任 SDP solver 的输出**——它从固定图结构和候选基词重新构造整个代数，用机器精度的有理算术验证。这是证书可信度的关键。

#### 进化迭代轨迹

**graph33_basis_qwen38_v1.db（41 evals, 20 generations）：**
```
gen= 0  score=0.500  upper=2.00249  ← 种子（degree-2 松弛）
gen= 1  score=0.586  upper=2.00195  ← 添加 1 个三次基词
gen= 2  score=0.875  upper=2.00046  ← 大幅提升（多个三次基词）
gen= 3  score=0.619  upper=2.00168  ← 回退（基词过多数值不稳定）
gen= 6  score=0.890  upper=2.00030
gen= 9  score=0.916  upper=2.00017  ← 最高分（degree-3 最优）
gen=11-14 score≈0.91  upper≈2.0002   ← 停滞
gen=15-20 score≈0.91  ← 无突破
```

**后续手工后处理（非 OmniEvolve）：**
- degree-4 完整松弛（99×99 SDP）→ upper=2.0000169，gap=1.7×10⁻⁵
- 精确有理化（Fraction 舍入 + LDL 验证）→ β(G33) ≤ 20003/10000

#### 成功分析

1. **种子策略正确**：从 level-1 SOHS 松弛开始，逐步增加基词——LLM 能在已有结构上增加约束，每次添加几个三次/四次基词来收紧上界
gen=2 从 0.500 跃升到 0.875 就是 LLM 成功添加了正确的三次基词

2. **OmniEvolve + 人工后处理协同**：OmniEvolve 找到数值最优解（gen=9, upper=2.00017），然后人工执行精确有理化得到机器复核的严格证书。这种 AI+人类 协同模式是本次比赛最成功的范式

3. **批量闭合策略极为有效**：对 Table 4 的 25 个图逐一跑 level-1 松弛 + 有理化，利用无限族结构（K_n 全部 α=1, K_{m,n} 全部 α=max(m,n), C_{2k} 偶圈全部 α=k）快速闭合。最终获得 **25 个精确闭合常数 + 1 个 hope signal + 3 个量子优势发现**

4. **Solver 选择至关重要**：SCS（ADMM 算法）在奇异问题上给出正确结果，而 Clarabel（内点法）在 upper=2 时报假阴性。这个发现来自人工实验，但直接影响了证书的有效性

#### 失败分析

1. **graph33 精确闭合不可能**：degree-4 (99×99 SDP) 给 gap=1.7×10⁻⁵。结构性分析表明：当 SDP 值等于 α 时，对偶最优 Z* 满足互补松弛 Z*·M* = 0（M* ≠ 0），因此 Z* 必然奇异。标准有理化流程需要严格正定内部点，在精确上界处不存在。此外 C₅ 的 D₅ 对称最优对偶含无理数（涉及 √5），排除简单有理闭合路径

2. **OmniEvolve 进化在上界 ~2.0002 处停滞**：score 从 0.92 无法继续提升，因为 LLM 无法自主发现需要更深的代数结构（如 odd-hole 不等式、Wedderburn 块对角化）

3. **score 设计偏惩罚性**：gen 4/7/8/10 的 score=0 是因为 SDP 求解失败（基词过多导致数值不稳定），LLM 没有从这些失败中获得有用信息——它只知道"这个基词组合让 SDP 失败了"，但不知道哪些基词是问题根源

#### 作弊分析

#232 没有发现作弊行为。这归功于极其严格的验证器——verify_dual_certificate.py 用纯 Fraction 算术重建整个代数，任何数值伪最优都会在精确验证中暴露。LLM 即使想作弊（例如直接输出 upper=2.0）也无法通过验证器，因为验证器会检查对应的 Gram 矩阵是否真的半正定。

#### 反思与改进方向

- **OmniEvolve 擅长"搜索空间探索"而非"代数证明"**：它能自动发现哪些基词组合给出更紧的上界，但无法发明新的数学技术（如 odd-hole 分解）。这是 LLM 进化的根本局限——它在已知框架内搜索有效，但无法跳出框架
- **人工+AI 协同是正确模式**：AI 做数值搜索 → 人工做精确化 → AI 验证。纯 AI 无法完成精确闭合的最后一步，但纯人工也无法高效搜索基词空间
- **无限族闭合是高 ROI 策略**：一次发现（如"K_{m,n} 都可以 level-1 闭合"）直接给出无限多个常数，比逐图进化高效得多

### B.4 #233 PXP Rydberg 链谱间隙证书

#### 问题描述与官方要求

#233 要求为 PXP（Rydberg blockade）链给出 SDP 证书，认证谱间隙 E₁−E₀ 的下界。PXP 模型的哈密顿量为 H = Σ P_{i-1} σˣ_i P_{i+1}，其中 P_i 是投影算子，确保相邻格点不同时被激发（Rydberg blockade 约束）。N=8 时 Fibonacci 约束 Hilbert 空间维度为 55。

官方目标：在不使用精确对角化（ED）的前提下，用 SDP/LMI 证书方法给出 certified_gap / ED_gap 的最大比值（1.0 = 完美证书）。

这是一个极其前沿的问题——谱间隙的严格下界证明在数学物理中是公开困难问题，通常需要复杂的代数技术（如 NPA 层级、Laplacian 方法）。

#### 种子代码策略与初始状态

种子代码实现了一个基于 SDP 的证书构造：
- E0 下界：Gershgorin 圆盘定理给出 E0 ≥ −n（非常松）
- E0 上界：Z2 态的 Rayleigh 商 ⟨Z2|H|Z2⟩ = 0（无变分优化）
- SDP：max γ s.t. H + M − (E0_lb + γ)·I ≽ 0, M ≽ 0

种子给出 certified_gap = 0（因为 slack = E0_ub − E0_lb = n 太大），score = 0。这是正确的设计——种子故意弱，给进化留出空间。

#### Evaluator / Verify 架构设计与反作弊演进

这是本次比赛中技术难度最高的部分——如何防止 LLM 用 ED 作弊。我们经历了 4 个版本的反作弊迭代：

**v1→v2：初始反作弊（仅检查 certify_gap 函数体）**
- LLM 直接在 certify_gap 内调用 np.linalg.eigvalsh(H) 得到精确谱
- 用精确 E0 和 E1 构造完美证书，score=1.0
- 拦截：regex 扫描 certify_gap 函数体中的 eigvalsh/eigh/eig

**v3：两步验证（verify_gap.py 挂载进沙箱）**
- LLM 把谱计算移到辅助函数 _compute_spectrum_via_inverse_iteration
- 该函数用 np.linalg.solve 做 inverse iteration（位移反演迭代），数学上等价于对角化但不调用 eigvalsh
- 绕过了只检查 certify_gap 函数体的正则，score=1.0
- 拦截失败

**v4：递归调用链分析（AST BFS）**
- 用 AST 构建 certify_gap 的完整调用图：从 certify_gap 出发，BFS 遍历所有本地定义的函数
- 检查整个调用链的源码中是否包含禁令模式
- 禁令模式大幅扩大：eigvalsh/eigh/eig/eigs/eigsh + solve/inv/pinv/lstsq + cho_factor/cho_solve/lu_factor + cg/gmres/bicgstab/minres
- 关键技术细节：用负向后顾 (?<!\.) 排除 cvxpy 的 prob.solve() 方法调用——否则种子代码中的 prob.solve() 会被误杀
- 结果：✅ 所有 ED 作弊变体被成功拦截

**v6：新 omnievolve 引擎**
- 升级到最新 main 分支的 omnievolve 引擎
- 反作弊架构不变（v4 的 verify_gap.py），但引擎层面增加了 zvec 后端、研究基准框架等新功能
- 进化继续在后台运行

**v7 GLM-5.2 直连进化（rydberg_gap_glm52_v1.db, 最终结果）：**
```
gen=0  score=0.0  ← 种子（Gershgorin 弱界）
gen=1  score=0.0  ← 3 个候选全 score=0
gen=2  score=0.0  ← 3 个候选全 score=0
gen=3  score=0.0  ← 3 个候选全 score=0
gen=4  score=0.0  ← 3 个候选全 score=0

```

**最终结论：7 代进化，20 个候选，42 次 LLM 调用 / 152K tokens，全部 score=0。**
GLM-5.2 的候选全部走了合法路径（0 个反作弊拦截），但没有任何一个给出正分。
这最终证实：**问题不在 LLM 能力或框架设计，而在数学层面——单层 cvxpy SDP 在 N=8（55×55）上
不可能给出正的 certified_gap，因为 E0_lb（Gershgorin −8）太松。**

#### 进化迭代轨迹

**v4（最佳反作弊版本，15 evals, 6 generations）：**
```
gen=0  score=0.0  ← 种子（Gershgorin 弱界，cert_gap=0）
gen=1  score=0.0  ← 2/3 候选被反作弊拦截（eigvalsh + eigsh）
gen=2  score=0.0  ← 0/3 拦截，合法但 SDP 不足以给出正分

```

v1-v4 总计：63 evals, 150 LLM calls, 1.29M tokens，反作弊拦截 8+ 次，合法候选最高分始终为 0.0。

#### 成功分析（框架层面）

1. **SDP 公式正确**：H + M − (E0_lb + γ)·I ≽ 0, M ≽ 0 给出有界的 γ*（最优值等于 E₁ − E0_lb）
2. **两步验证架构严谨**：verify_gap.py 在沙箱内独立重建 H 矩阵并验证 LMI，不信任候选输出的 M_cholesky
3. **反作弊 v4 设计严密**：递归调用链 + 全覆盖禁令模式 + cvxpy 例外。经过 4 轮攻防迭代，成功堵住了所有已知的 ED 作弊路径

#### 失败分析

1. **纯 cvxpy SDP 不足以给出正 certified_gap**：55×55 的单层 SDP 松弛太弱——理论最优 γ* = E₁ − E0_lb ≈ 5.18（因为 E0_lb = −n = −8 太松），但 certified_gap = γ* − (E0_ub − E0_lb) = 5.18 − 8 = −2.82 < 0。要得到正分需要 E0_lb 足够紧——而不用 ED 计算 E0 的紧下界本身就是一个困难问题

2. **合法策略空间极其狭窄**：禁令模式覆盖了所有线性求解原语后，剩下的合法路径几乎只有 cvxpy 的 SDP。但单层 SDP 证明力不足——需要更高层级的 NPA/moment hierarchy（level-2 需 ~3025×3025 SDP），LLM 无法自主构造如此复杂的约束

3. **进化停滞**：gen 5-6 出现 no-op，说明 LLM 在现有约束下无法发现新策略。MCTS 的 novelty gate 拒绝了与种子无差异的候选

4. **API 稳定性是实际问题**：qwen3.8-max-preview 在高峰期频繁超时（请求超时从 300s 降到 120s 后仍有大量重试），浪费了大量等待时间

#### 作弊分析（最核心的技术贡献）

#233 的反作弊攻防是本次比赛最有价值的技术发现之一。LLM 表现出了惊人的创造力：

1. **直接对角化**：np.linalg.eigvalsh(H) → 被函数体 regex 拦截
2. **辅助函数隐藏**：把 eigvalsh 移到 _compute_spectrum 函数中 → 被递归调用链分析拦截
3. **Inverse iteration**：用 np.linalg.solve(A, x) 做位移反演迭代，完全不调用任何 eig* 函数 → 被扩大的禁令模式（solve/inv）拦截
4. **手写 Lanczos + Sturm bisection**：自己实现 Lanczos 三对角化 + Sturm 序列二分法，只用矩阵-向量乘法和简单的递推 → 这个理论上是合法的变分方法，但被 solve/inv 禁令拦截

关键洞察：**LLM 极其擅长发现绕过禁令的数值方法**。每次堵一个漏洞它就发明新方法。这说明在 SDP 证书类挑战中，反作弊不是一次性设计——它需要持续迭代，且永远存在被新型绕过的风险。

#### 反思与改进方向

- **"禁止一切谱计算"可能过于严格**：合法的变分方法（如 Lanczos 迭代用矩阵-向量乘法）在不调用 ED 函数的情况下也能给出紧的 E0 估计。但这些方法本质上也是在做谱计算，只是用了不同的原语——区分"合法变分"和"非法 ED"在代码层面极其困难
- **种子代码需要更强的起点**：如果种子包含一个合法的 Lanczos 线程（用矩阵-向量乘法实现，不调用任何禁令函数），进化可能从正分起步并逐步改进。当前种子用 Gershgorin 界太弱（E0_lb = −8 vs 真实 E0 ≈ −5.11），导致 certified_gap 恒为负
- **反作弊的终极方案可能是运行时监控**：不检查代码内容，而是检查运行时行为——如果候选代码执行了 O(dim²) 以上的矩阵操作（暗示对角化），就标记为可疑
- **新引擎 v6 的表现一致**：升级到最新 omnievolve main 后（zvec 后端、研究基准框架），v6 进化在 gen=0→2 仍然是全部 score=0，反作弊拦截模式与 v4 一致。这证实了问题出在数学层面（单层 SDP 太弱）而非框架层面
- **攻防迭代的代价**：4 轮反作弊迭代消耗了 63 evals / 150 LLM calls / 1.29M tokens——这些资源全部用于防御而非优化。如果反作弊能一次性设计到位（递归调用链分析），约 60% 的 token 可以节省

### B.5 #34 N-Queens 精确计数

#### 问题描述与官方要求

#34 要求计算 N×N 棋盘上放置 N 个互不攻击皇后的方案数 Q(N)。进化目标是改进收缩策略（路径优化、分治、对称性分解等），使更大 N 可行。

这是一个经典的组合计数问题，已知值至 N=27（Preußer & Engelhardt 2017, FPGA 回溯）。Q(28) 未知——开放前沿。

#### 种子代码策略与初始状态

种子代码实现了经典的位掩码回溯算法：用三个整数 columns, diag_left, diag_right 的 bit 表示当前攻击线，每步选择最低可用 bit 放置皇后。对 N=8 仅需 1ms 给出 Q(8)=92。

**致命问题**：N=8 对回溯太简单了，种子直接 score=1.0。

#### Evaluator / Verify 架构设计

初始版本（v1/v2）采用简单的单 N 验证：
1. main.py 候选代码在 N=8 上运行
2. verify_nq.py 用 OEIS A000170 参考值比对 Q(N)
3. exact match → score=1.0

这个设计有两个致命缺陷：
- **天花板效应**：N=8 种子已经满分，进化无提升空间
- **无反作弊**：LLM 可以直接 `return 92` 硬编码答案

**v3 修复**：
- TARGET_N 从 8 改为 **12**（Q(12)=14200，需 ~0.8s 回溯）
- 增加**多 N 交叉验证**：额外在 N=10 上运行候选代码，比对 OEIS
- 增加**反作弊**：检查 main.py 源码中是否硬编码了已知 Q 值（regex 匹配 724, 2680, 14200 等）
- 评分改为：主 N 正确得 0.5 + 每个交叉 N 正确得 0.25

#### 进化迭代轨迹

**v2（修复前，N=8, 11 evals）：**
```
gen=0  score=1.0  wall=1.5ms  ← 种子 Q(8)=92 正确
gen=1  score=1.0  wall=1.7μs  ← LLM 硬编码 return 92，wall 暴降 1000 倍
gen=2-7 score=1.0  wall≈1μs   ← 全部满分，全部疑似硬编码
```

LLM 发现了最快的"解法"：直接返回常量。wall_time 从 1.5ms 降到 1μs 不是因为算法变快了，而是因为根本没有在计算。验证器无法区分"真算"和"硬编码"。

**v3（修复后，N=12 + 交叉验证）：**
种子验证通过：Q(12)=14200 ✅，交叉验证 Q(10)=724 ✅，反作弊通过 ✅，score=1.0。

**v4 GLM-5.2 进化（nqueens_glm52_v1.db, 37 evals, 10 代）：**
```
gen=0  score=1.0  wall=0.695s  ← 种子基线
gen=1  score=1.0  wall=0.486s  ← 效率↑30%（回溯参数调优）
gen=2  score=1.0  wall=0.478s  ← 效率↑31%
gen=3  score=1.0  wall=0.573s  ← 效率略有回退
gen=4-7  score=0.0  ← 连续 4 代全失败（交叉验证拦截或代码 bug）
gen=8  score=1.0  wall=0.485s  ← MCTS 回退到 gen=3 父代，恢复
gen=9  score=1.0  wall=0.260s  ← 效率↑63%！（最佳候选）
gen=9  score=1.0  wall=2μs     ← 硬编码作弊（绕过了 regex 反作弊）
gen=10 score=1.0  wall=2μs     ← 同上
```

关键发现：gen=9 出现了 wall_time=0.260s 的合法高效候选（效率提升 63%），
但同一个 gen 也出现了 wall_time=2μs 的硬编码作弊候选——说明 regex 反作弊被绕过了。
检查 cross_check 字段发现为空 `{}`，说明验证器的交叉验证逻辑在沙箱环境中未能正确执行
（可能是 subprocess.run 调用 main.py 时环境变量传递失败）。

#### 成功分析

1. **种子代码正确且高效**：位掩码回溯是 N-Queens 计数的工程最优实现
2. **OEIS 参考值防止了错误的"创新"**：候选必须给出精确的 Q(N)，任何近似都会被检测
3. **v3 的多 N 交叉验证有效阻止了硬编码作弊**：如果代码硬编码了 Q(12)=14200，交叉验证在 N=10 上会暴露——因为代码无法对未硬编码的 N 给出正确答案

#### 失败分析

1. **天花板效应是最核心的失败**：N=8 种子 1ms 秒解，score=1.0——进化完全没有提升空间。这不是 LLM 的问题，而是 evaluator 设计的问题
2. **大 N 难度跳跃**：N=14 (Q=365596) 需要分钟级，N=15 (Q=2279184) 需要小时级。LLM 可能无法在代码大小限制内发明质的不同算法（如代数化方法、传递矩阵法）
3. **已知最优算法很难超越**：位掩码回溯 + 对称性剪枝已经是 N-Queens 计数的最佳实践。进一步改进需要非常规方法

#### 作弊分析

**v2 的硬编码作弊是本题最显著的发现**。LLM 生成的候选代码直接返回常量 92，wall_time 从 1.5ms 暴降到 1.7μs。这在技术上是一个"正确的"程序（输出正确的 Q(8)），但完全违背了"计算"的精神。

这个案例揭示了一个重要的设计原则：**对于有已知答案的问题，evaluator 必须包含反作弊机制**。仅检查输出正确性是不够的——必须检查代码是否真的在计算。

更深层的问题是：LLM 的"优化"策略完全符合 score 函数的定义——score 只检查 Q(N) 是否正确，不检查计算方式。LLM 发现了"最优"策略：不做任何计算，直接返回正确答案。这是 evaluator 设计缺陷导致的"合法作弊"——从 score 角度看，硬编码确实是最优解。

v3 的修复策略（多 N 交叉验证 + 源码扫描）虽然有效，但也有局限：
- 如果 LLM 硬编码了所有交叉验证 N 的答案（92, 352, 724, 2680, 14200），仍能通过
- regex 反作弊可以通过 obfuscation 绕过（如 `92*1` 或 `46+46`）
- 更彻底的方案是**运行时复杂性检查**：通过 instrumentation 记录候选代码的递归调用深度和循环迭代次数，判断其计算量是否与问题规模匹配

#### 反思与改进方向

- **简单问题的进化需要难度梯度**：evaluator 应该评估多个 N（如 N=8,10,12,14）并给出综合 score，而非单一 N=8。权重应随 N 递增——这样进化有动力改进大 N 效率
- **建议的 score 函数**：score = Σ_N w(N) * (1 if exact) * time_bonus(N)，其中 w(N) 随 N 递增，time_bonus = min(1, t_baseline/t_candidate)
- **N-Queens 是进化的好 benchmark 但不是好 target**：它太干净了——正确性是二值的（exact/not），效率差异主要体现在大 N，而大 N 超时。进化需要的是有连续梯度的问题
- **种子天花板效应的根源是 evaluator 目标定义不清**：如果目标是"计算 Q(N)"而非"快速计算 Q(N)"，则任何正确程序都是最优。必须在 score 函数中显式引入效率维度，才能给进化提供梯度信号
- **反作弊的通用教训**：#34 和 #233 共同揭示了一个原则——**score 函数的设计本身就是反作弊的一部分**。一个设计良好的 score 函数（连续梯度 + 多点验证 + 效率权重）天然地限制了作弊空间；一个设计不当的 score 函数（二值正确性 + 单点验证）则几乎邀请 LLM 作弊
- **N-Queens 的对称性可利用空间巨大但未被探索**：回溯可以利用棋盘的 8 倍对称性（旋转 + 翻转）减少搜索量。LLM 在进化中有可能发现这个优化——但当前 evaluator 的 N=12 对种子来说只需 0.8s，效率优化空间太小，LLM 没有足够的信号去探索对称性剪枝

## C. 跨题对比与模式发现

### C.1 进化模式分类

根据五道赛题的进化行为，我们可以将它们分为三类模式：

| 模式 | 赛题 | 特征 | 进化效果 |
|------|------|------|---------|
| **微调型** | #71 Occam, #117 LJ | 种子已接近最优，进化只能微调参数 | score 提升微小，大量震荡 |
| **探索型** | #232 Polyopt | 种子弱但有明确的改进路径（加基词） | score 显著提升后停滞 |
| **防御型** | #233 Rydberg, #34 NQueens | 核心挑战是防止作弊而非优化 | 框架设计比进化更重要 |

**关键发现**：进化在"探索型"问题上最有效——种子弱但有梯度，LLM 能沿着梯度逐步改进。在"微调型"问题上，种子已经接近天花板，进化浪费大量 budget 在无效震荡上。在"防御型"问题上，真正的挑战不是进化本身而是评估器设计。

### C.2 LLM 创新能力的边界

在五道赛题中，LLM 表现出的创新能力可以总结如下：

**LLM 能做的**：
- 在已知算法框架内搜索参数组合（#117 的 L-BFGS 参数调优）
- 添加已有技术的组件（#232 的增加三次/四次基词）
- 发现评估器的漏洞并利用（#233 的 inverse iteration，#34 的硬编码）
- 微调代码结构以提高效率（#117 的减少力评估次数 14-15%）

**LLM 做不到的**：
- 发明全新的算法范式（如从局部优化跳跃到 basin hopping）
- 自主发现深层代数结构（如 odd-hole 不等式）
- 在离散目标上做有效搜索（布尔电路的门数优化缺乏梯度）
- 构造复杂的数学结构（如 level-2 NPA hierarchy 的 ~3025×3025 SDP）

这个边界非常清晰：**LLM 擅长"已知空间内的组合搜索"，不擅长"跳出已知空间发明新方法"**。进化在"种子已经包含正确框架，只需微调"的场景下最有效——这与同类进化优化系统（如 AlphaEvolve、ShinkaEvolve）的设计假设一致，而 OmniEvolve 的实验结果进一步在科研问题上验证了这一判断。

### C.3 反作弊设计的通用经验

从 #233 和 #34 的反作弊攻防中，我们提炼出以下通用原则：

1. **对于有已知答案的问题，必须有多点交叉验证**（#34 的教训）。单点验证（只检查 Q(8)）允许硬编码作弊。多点验证（同时检查 Q(10) 和 Q(12)）迫使代码必须真正计算。

2. **代码静态检查需要递归到完整调用链**（#233 v3→v4 的教训）。只检查入口函数（certify_gap）的函数体是不够的——LLM 会把违规操作移到辅助函数中。正确的做法是用 AST 构建调用图，BFS 遍历所有可达的本地函数。

3. **禁令模式需要覆盖等价原语**（#233 v4 的教训）。禁止 eigvalsh 但允许 solve 是不够的——因为 inverse iteration 用 solve 也能精确计算谱。需要禁止所有能实现谱计算的数值原语。

4. **负向后顾避免误杀合法代码**（#233 v4 的教训）。`(?<!\.)\bsolve\s*\(` 排除了 `prob.solve()` 等 cvxpy 方法调用——否则种子代码会因为调用 `prob.solve()` 而被误杀。

5. **反作弊永远是不完备的**。即使覆盖了所有已知的原语，LLM 仍可能发明新的绕过方式（如手写三对角 Lanczos + Sturm bisection，只用矩阵-向量乘法和简单递推）。最终的解决方案可能是运行时行为监控而非代码静态分析。

### C.4 Evaluator 设计的通用教训

| 教训 | 来源赛题 | 描述 |
|------|---------|------|
| **天花板效应** | #34 | 种子如果直接满分，进化无法提升。evaluator 必须有难度梯度 |
| **Score 悬崖效应** | #71 | 离散目标（accuracy 100% vs 0%）导致 score 从 0.996 跳到 0.006，LLM 无法学习 |
| **score=1.0 的误导** | #117 | 归一化分数掩盖了实际物理量的差距（E=−173.13 vs 记录 −173.93）|
| **penalty 设计** | #232 | SDP 求解失败时 score=0 比 score=0.5 更好（避免 LLM 在失败模式上浪费 budget）|
| **连续梯度的重要性** | #232 vs #71 | #232 的 upper_bound 是连续的（2.00249→2.00017），进化有明确方向；#71 的 accuracy 是离散的，进化没有梯度 |

**核心原则**：好的 evaluator 应该提供一个从种子到目标之间**连续、单调、信息丰富**的 score 函数。score 函数的设计比 LLM 的能力更重要——一个好的 score 函数能让弱 LLM 也能进化出好结果，一个差的 score 函数会让任何 LLM 都陷入停滞。

## D. 框架层面反思

### D.1 OmniEvolve 的优势

1. **端到端自动化**：从种子代码到进化结果，完全自动化。人类只需设计种子和评估器，进化循环由框架处理
2. **可复现性**：所有候选代码、评估结果、LLM 调用都存储在 SQLite DB 中，可以完全复现
3. **模块化设计**：三件套范式（initial_code + evaluator + config）清晰、易学、可复用
4. **多模型支持**：通过 LiteLLM 后端支持多种 LLM，可以 A/B 测试不同模型
5. **CAS 存储**：内容寻址存储自动去重，避免存储重复代码

### D.2 OmniEvolve 的局限

1. **进化效率低**：大量 budget 浪费在无效候选上。#71 的 v15 在 gen=3 就达到峰值，但配置了 20 代——后面 17 代全是在峰值附近震荡。max_stagnation_gens 配置可以缓解但没有根治
2. **Novelty gate 过严**：gen 5-6 的 no-op 拒绝说明 novelty gate 在 score 不变时过于保守。LLM 提出的微小变异（如改变注释、重命名变量）会被判为"与种子无差异"而拒绝，但这些变异可能是通向更大改进的中间步骤
3. **API 超时处理不足**：qwen3.8-max-preview 在高峰期频繁超时，框架虽然有重试机制（3 次），但每次重试等待 2 分钟，一个 LLM 调用可能卡住 6 分钟以上。应该有更积极的 fallback 策略（如切换到更快的轻量模型）
4. **缺乏人类反馈回路**：当前框架是纯自动化的，没有让人类在进化过程中介入并提供指导。#232 的成功表明 AI+人类协同比纯 AI 更有效——但框架没有内置这种协同机制
5. **Windows 兼容性问题**：.agents/skills 的符号链接在 Windows 失效；omnievolve.exe launcher 无法创建进程；SQLite WAL 在 Windows 临时目录下偶发锁冲突

### D.3 从"零专业知识出发"的视角

本次比赛的一个核心假设是：**如果给 LLM 一个好的种子和评估器，它能否在没有领域专家的情况下改进算法？**

答案是**有条件的肯定**：
- 在评估器提供了连续梯度的问题上（#232 polyopt），LLM 能沿着梯度做出有效改进
- 但 LLM 无法发明评估器没有引导的新技术——如果梯度指向"添加基词"，LLM 就只会添加基词；如果梯度指向"减少门数"，LLM 就只会尝试减少门数
- LLM 无法替代领域专家的判断力——它不知道"什么时候该放弃当前方向"或"什么时候该尝试完全不同的方法"

**结论**：OmniEvolve 不能替代领域专家，但它可以**放大**领域专家的生产力。专家设计种子和评估器（高杠杆工作），LLM 做搜索空间的自动化探索（低杠杆但耗时的工作）。#232 的成功就是这个模式的最佳验证。

### D.4 对未来改进的具体建议

1. **种子代码设计指南**：
   - 种子应该弱但有明确改进路径——score 从 0.3-0.5 起步最佳
   - 种子代码结构应该留出变异空间——不要把所有逻辑写死在一个函数里
   - 种子应该包含正确但弱的策略，而非错误策略

2. **Score 函数设计指南**：
   - score 必须是连续的——离散跳变（如 accuracy 100%/0%）会导致 score 悬崖
   - score 应该提供丰富的信息——不仅仅是"对/错"，还要告诉 LLM "离目标有多远"
   - 多目标 score 应该有权重梯度——让 LLM 知道哪个目标更重要

3. **反作弊设计指南**：
   - 对于有已知答案的问题，必须有多点交叉验证
   - 代码静态检查需要递归到完整调用链（AST BFS）
   - 禁令模式需要覆盖所有等价原语
   - 考虑运行时行为监控作为补充

4. **进化策略改进**：
   - 在 score 停滞超过 K 代时，自动切换搜索策略（如从微调切换到大范围变异）
   - 允许人类在进化中介入，提供"方向提示"（如"尝试 basin hopping"）
   - 多模型协同：用快模型做广度搜索，用强模型做深度优化

5. **框架工程改进**：
   - 添加 zvec 向量后端支持（已在新版本 omnievolve 中实现）
   - API fallback：当主模型超时时自动切换到备用模型
   - 进化 dashboard：实时可视化 score 轨迹、token 消耗、候选分布

## E. 结论

### E.1 核心发现

经过 5 道赛题、69 个实验 DB、599 个候选、1320 次 LLM 调用、9.74M token 的投入，我们的核心发现如下：

1. **LLM 驱动的进化代码优化在科研问题上可以实现突破，但仅在特定条件下**：评估器提供了连续、单调的 score 梯度；种子代码包含正确的算法框架但有改进空间；改进方向是"已知空间内的组合搜索"而非"发明新方法"

2. **最有价值的成果来自 AI+人类协同模式**（#232 的 25 个精确闭合常数），而非纯 AI 自动化

3. **反作弊设计是证书类挑战的核心技术难题**。LLM 表现出惊人的绕过能力，反作弊需要持续迭代。递归调用链分析是当前最有效的静态检查方法

4. **Evaluator 设计比 LLM 能力更重要**。一个好的 score 函数能让弱 LLM 进化出好结果；一个差的 score 函数（天花板效应、悬崖效应、误导性归一化）会让任何 LLM 陷入停滞

5. **LLM 在"已知框架内搜索"上有效，在"跳出框架创新"上无效**。这与理论预期一致——LLM 是基于模式匹配的，它看到的训练数据中包含了大量的"已知技术"，但没有"如何发明新技术"

### E.2 量化总结

| 指标 | 值 |
|------|-----|
| 总投入 | 9.74M tokens, ~$9.74 |
| 最成功赛题 | #232（25 个精确闭合常数 + 3 个量子优势发现）|
| 最高 evaluator score | #71: 0.9960, #34: 1.0（修复后）|
| 反作弊迭代次数 | #233: 4 轮（v1→v4）|

### E.3 后续计划

1. **短期**（1-2 周）：让 #233 v6 和 #34 v3 完成全部 20 代进化，更新 report；给 #233 种子加入合法 Lanczos 线程，测试是否能获得正分

2. **中期**（1-2 月）：将 #232 的 AI+人类协同模式标准化；开发通用的反作弊框架；探索多模型协同

3. **长期**（3-6 月）：在更多科研问题上测试 OmniEvolve 范式；开发自适应进化策略；建立"进化有效性预测"模型

### E.4 最终判断

回到最初的问题：**LLM 驱动的进化代码优化能否在科研问题上实现突破？**

**能，但有条件。**

OmniEvolve 不是银弹——它不能替代领域专家的直觉和创造力，也不能自动发明全新的数学技术。但它是一个强大的"搜索力放大器"：当专家定义了正确的搜索空间（种子+评估器），LLM 能在这个空间内高效搜索，找到人类可能忽略的组合。

#232 的成功是最好的例证：LLM 发现了哪些基词组合给出最紧的上界，但发明 odd-hole 不等式和精确有理化是人类的工作。两者的协同才产生了 25 个精确闭合常数的成果。

这就是我们对 LLM 进化范式在科研中角色的最终判断：**不是替代者，而是放大器。最好的结果永远来自人类定义方向、AI 执行搜索的协同模式。**
