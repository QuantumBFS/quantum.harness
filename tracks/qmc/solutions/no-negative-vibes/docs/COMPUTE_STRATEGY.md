# 项目定性与算力策略

## 项目是什么类型

这是一个“高吞吐候选筛选 + 少量高精度闭合”的项目，不是传统的单个超大规模模拟。

每个基础检验只是生成几个小矩阵、计算矩阵指数和一个行列式，通常很便宜；真正可能爆炸的是：

```text
候选结构 × 维数 × 乘积深度 × 参数尺度 × 随机种子 × 样本数
```

所以用户提出的判断是对的：如果我们建立出很多不冗余候选，超算能把总墙钟时间大幅压缩；
如果候选表还只有几十项，提前占用超算不会解决主要困难。

## 本机吞吐基准

在当前 WSL2/Anaconda 环境，用单线程、float64、8 个稠密随机生成元的
`prod exp(A_i)` 做一次粗基准：

| 矩阵维数 | 样本/秒 | 100 万样本的单核小时 |
|---:|---:|---:|
| 16 | 8,610 | 0.03 |
| 32 | 2,884 | 0.10 |
| 64 | 662 | 0.42 |
| 128 | 127 | 2.19 |
| 256 | 15 | 18.46 |

这是数量级基准，不是集群性能承诺；它不包含符号化、任意精度、磁盘排队和复杂约束投影。
实际 `classical-groups-v1` 的 90 万个小矩阵乘积，900 格累计约 178 单核秒。

## 三个算力层级

| 层级 | 典型规模 | 用什么 | 目标 |
|---|---|---|---|
| 本地筛选 | `<=10^6` 小矩阵样本、几十个候选 | 当前机器 | 调试生成器、杀明显反例、建立精确证书 |
| 普通集群 | `10^7–10^9` 样本、上千至上万个候选格 | CPU job array | 锥交集/半群表、深度/尺度覆盖、独立复核 |
| 国家超算 | `>10^9` 样本、`n>=256`，或大规模自生成候选搜索 | 大型 CPU 阵列 | 把组合爆炸压缩到可接受墙钟时间 |

这不是硬阈值。进入任意精度时，即使样本较少也可能值得上集群；反之，十亿个彼此高度冗余的
随机样本不值得算。

## 什么时候正式申请超算

满足下面任一条就应把超算从“备用”升级为主力：

1. 新候选生成器经过约化去重后仍有 `>=10,000` 个独立结构格点；
2. 计划样本量达到 `10^8`，本地预计墙钟超过一天；
3. 需要在维数 `128–512`、深度 `32–256` 上验证稀有负例；
4. 大量近零/近实轴异常必须用 128–512 bit 精度复核；
5. 多个团队成员要并行复现实验并保留独立种子。

目前只建议提前确认超算账号、Python/SciPy 环境和 CPU 队列政策；不需要申请 GPU、大内存节点或
大额度预留。矩阵格点彼此独立，最合适的形态是“每个参数格一个 CPU 数组任务”。

## 已为集群准备好的接口

当前协议已经把每个格点拆成独立、确定性的 manifest：

- 相同种子可重放；
- 任务中断后只补缺失格；
- 每格保存最早的负权、复权或不确定样本；
- 汇总前检查成功、失败、缺失和待运行状态；
- 只有异常格需要升级高精度。

这意味着以后迁移到 Slurm/PBS 主要是调度包装，不需要重写科学计算核心。

## 当前决策

现在的最优策略是：

1. 本地完成候选定义、去重、低维反例搜索；
2. 选定复杂 Majorana、锥交集或物理 HS 主线后，估算真实候选格数；
3. 若达到上述触发条件，就使用国家超算 CPU 数组做宽扫；
4. 把高精度资源只花在幸存项和数值异常上。

一句话：超算会是“候选空间扩大后的加速器”，但不是“当前项目能否启动的前提”。
